# QA 与交付方案提案

状态：待策划、架构及项目经理确认。已知范围为单人本地运行的中文文字修仙游戏，HTML/CSS/JavaScript 前端与 Python 后端，无付费或在线依赖。以下是验收策略，不代替 GDD 定义玩法。当前不编写测试实现，不宣称任何游戏功能已通过。

## 依赖与独占范围
实施前需要：已批准 GDD（资源、状态、胜负、失败恢复及通关规则）、API/错误/并发契约、存档格式与生命周期、启动命令、页面交互规范。QA 后续独占 `tests/` 和项目经理指定的交付测试文档；应用、页面和玩法修复由对应负责人实施。

建议先确定每次操作的合法前置条件、消耗与收益、失败是否消耗资源、终局后可执行行为；不能让 QA 从代码推断唯一正确答案。随机机制应有可复现验证方式，但发布游戏不能通过关闭断言或修改玩法来通过测试。

## 测试层级与证据
1. 规则测试：对批准的规则核对状态转移、资源守恒或有界性、不合法操作无副作用。尽量从输入输出验证，不复制实现公式形成自证。
2. HTTP 集成：启动真实 Python 服务，通过公开接口完成状态读取、操作与保存恢复；同时验证状态内容、错误响应和磁盘持久化。
3. 页面端到端：在真实浏览器中加载页面，通过可见按钮与输入完成主要循环和完整通关，观察中文反馈、状态、进度、日志及终局。API 通关不能替代页面通关。
4. 交付复现：按文档从干净独立数据目录启动，验证不依赖开发者存档或外部网络；重启后可恢复。保存命令、版本、测试数量、失败详情、截图或运行记录，区分通过、失败、跳过、阻塞和未运行。

## 必需验收矩阵
| 类别 | 操作与观察标准 |
| --- | --- |
| 完整通关 | 从新档开始，通过公开玩家操作达到 GDD 终局，关键阶段均有可见推进；没有修改存档、直接改状态、绕过资源或直接调用内部胜利函数。记录路线与操作数量；终局明确且不会误触继续扣费或污染存档。 |
| 资源与边界 | 覆盖零、刚好足够、差一个、上限及连续操作；资源不出现负数、非有限数或无依据溢出；失败与成功消耗符合规则；按钮可用状态与后端判定一致。对所有可重复资源获取途径核对恢复性。 |
| 异常操作 | 未知动作、错误类型、缺字段、非法 JSON、空白/超长/特殊字符名称及不合法状态操作；响应可理解，无堆栈泄漏，原状态不被部分写入；页面错误后仍能再次操作。 |
| 重复与并发请求 | 快速双击、相同请求重发、并发合法操作及过期状态提交；依据架构契约确保操作至多一次或逐次原子执行，不丢更新、不重复扣除、不突破资源限制。发生冲突时页面刷新并说明结果。 |
| 多页 | 同一存档开两页，交替操作、旧页继续提交、其中一页重置或恢复；不得以旧状态覆盖新状态，也不能显示成功但实际未保存。明确单一存档的身份与跨页同步规则。 |
| 保存与恢复 | 操作后刷新、关闭重开、服务停止重启，比较全部影响玩法字段与进度；存档版本、默认值和保存时机按契约验证。测试使用独立临时目录，不覆盖用户存档。 |
| 存档损坏 | 空文件、截断 JSON、错误字段类型、缺必填字段、超范围值及不支持版本；应用不给出伪正常状态、不静默覆盖可恢复原档。按批准策略提供明确错误、备份/隔离或重建入口。写入中断不得产生可见半份存档。 |
| 窄屏与可访问操作 | 至少桌面与约 360px 窄屏，主操作、资源、反馈均可读取，无遮挡和必要按钮溢出；长中文、长日志可正常换行或滚动。键盘可访问主要控件，焦点可见，禁用原因有说明，不能只靠颜色传递结果。 |
| 真实交互 | 点击后请求中有反馈，操作完成更新数值与中文日志，失败可恢复；断网/服务暂不可用反馈清楚，无永久锁定按钮。危险重置需明确确认，取消不改变状态。 |

具体 API 状态码、重放策略、设备范围、胜利与失败路径在契约批准后补入用例，不预设实现。

## 优先排查的锁死风险
- 必需资源耗尽且没有免费恢复动作；失败惩罚导致永远达不到下一阶段。
- 消耗不可再生道具后才发现门槛不足；升级顺序造成必需操作永久不可达。
- 进度已达门槛但按钮未解锁，或终局条件与页面提示不一致。
- 概率连续失败且无退出/恢复路径；若 GDD 允许随机终局，须明确可接受保障和验证方法。
- 旧页面或重复提交损坏状态；请求失败留下操作锁；坏档或重启后无法进入游戏。

对每个非终局可达阶段检查：至少存在合法推进或可见恢复途径。若设计存在有意失败终局，需有明确重新开始入口，不能将其与程序锁死混为一谈。

## 防止伪通过
不以静态 HTML 文本、HTTP 200、端口存在、少量按钮截图或单条 happy path 声称可玩。检查当前运行版本和当次产物，不使用旧截图/旧测试结果。测试实际断言可观察行为，零测试或全部跳过不算通过。需要浏览器但工具缺失时明确记为未运行并报告项目经理，不能用 API 请求代替后仍标记页面通过。

## 缺陷与发布门槛
缺陷记录包含编号、严重性、目标版本、前置存档/环境、复现步骤、预期/实际、证据及回归结果。阻止启动/通关、存档丢失、资源破坏或无法恢复的锁死优先阻断交付；修复后覆盖原路径及相关回归。交付前必须完成真实页面主要循环和通关、持久化重启、异常/重复操作、窄屏检查，并给出清晰启动与重置说明及已知限制。性能和稳定性测试量依据实际机制设定，避免提出未经验证的任意指标。

### 策划：免费恢复与确定性战斗
赞同免费修炼、采药、静养及零灵力普攻/防御/撤退闭环，可避免资源枯竭软锁。冻结时需写清：静养是否一次回满、战斗中是否禁止安全行动、败退和撤退后的气血下限与地点、关键敌人挑战条件及奖励领取次数。QA 将从零灵石/零药草/零药物/零灵力及最低气血分别走公开恢复路线，验证在有限操作内回到可推进状态，而不是仅断言恢复按钮存在。

战斗应给出每个招式的确切成本、伤害与防御顺序、取整/最小伤害、敌方意图周期、药物是否消耗回合、先击杀是否免反击、同时濒死的裁定。敌人恢复动作不能形成所有合法策略都无法结束的无限循环。QA 将独立按 GDD 算出短序列预期，验证灵力不足拒绝无副作用、致命一击不反击、撤退无重复奖励、失败可恢复，并执行一条无需概率、修改存档或内部作弊的完整通关路线。行动预算不等于已验证真人游玩时长。

### 架构：事务、手动 slot 与失败边界
赞同后端权威、版本冲突、同 ID 同载荷幂等、原子事务和拒绝坏档。自动保存与 slot 必须定义为不同对象：保存 slot 是否改变当前 revision、恢复是否创建新 game_id、恢复后 slot 是否保留、首次空 slot 与非法 schema 的错误语义。手动 slot 是同一数据库内的逻辑快照，不能宣称能恢复整个数据库损坏；README 与 UI 均应明确这一点。

需固定去重结果与新局/恢复顺序，防止旧请求缓存被误用到新游戏；读档后旧标签页应被拒绝，不能覆盖刚恢复的进度。QA 将测试动作/存档/恢复并发、同 ID 不同载荷冲突、重复恢复和重启后的重复请求。损坏数据库使用隔离副本验证启动/接口错误与文件未被覆盖，不要求未批准的自动恢复或备份功能。

### 视觉：确定性文案与未确认结果
赞同行动成本邻近显示、禁用原因、存档成功后才显示已保存、窄屏单栏和真实错误反馈。冻结后删除突破概率和随机风险措辞，不为无风险的确定性突破增加多余确认。新局与覆盖 slot 保留明确确认，取消无写入；读档按契约说明会替换当前进度。

网络失败与后端拒绝必须区分：超时不能直接写“操作失败”，因为事务可能已提交；前端应先刷新权威状态，若提供重试必须复用相同 request_id。QA 将模拟响应丢失后重读状态，并确认没有假失败后新 ID 重试导致二次扣费。多页冲突不能悄悄自动重放玩家操作。持续日志和错误区需在窄屏可见，追加消息不应使主操作失焦或跳出视口。
