# 视觉与交互方案：归墟修行手札

状态：候选方案，供策划、架构与项目经理评审。玩法、具体数值与接口以批准的 GDD 和契约为准；本文不新增玩法系统。核心界面无需外部字体、图片、在线服务或付费资源。

## 视觉方向
采用深墨青底、古纸正文与克制的旧金强调，营造夜读修行手札的安静气质。主背景建议 `#101f20`，抬升表面 `#182c2c`，正文 `#eee6d2`，次要文字 `#b8c5b9`，交互强调 `#dec28a`；成功与危险同时提供文字和符号，不能仅用颜色区分。实际实现后校验文字对比度。

标题使用系统中文衬线字体栈，正文使用系统无衬线栈；不加载远程字体。标题留白、细线、章节编号和小型朱砂印章建立层级，正文优先可读性，不使用大面积难辨的书法字。避免把每个数值装进独立卡片：角色状态为一张横向账页，主要操作为章节式动作列表，记录为连续时间线。

## 布局与主路径
桌面内容宽度约 1180px，顶部为游戏名、存档状态与新局入口；首行突出人物名称、当前境界与下一目标。正文采用主次双栏：左侧约三分之二宽展示当前场景与主要行动，右侧展示人物状态和近期经历。左右栏按叙事与操作分工，避免后台控制台式导航。

主路径为：首次进入时了解当前目标 → 查看可执行行动 → 阅读耗时、消耗和效果 → 执行 → 得到具体结果及状态变化 → 判断下一步或满足突破条件。新局仅询问规则实际需要的信息；无需求的职业、头像、难度选择不增加。

当前最重要的行动在页面上只突出一个主按钮，其他动作为清晰次级按钮。境界、修为和生存类状态使用名称、当前值、上限与进度条；资源合并成紧凑账目，变化用 `+3 / −2` 文本显示。完整事件保留可展开记录，默认近期内容，不让新增日志挤走正在操作的位置。

## 行动成本、条件与风险
每个行动在按钮附近列出：主要收益、实际成本、所需条件，以及 GDD 定义的失败风险。确定性收益和概率结果分别表述，概率由服务端返回或规则明确给出，前端不编造。不可执行时显示缺失条件，例如“修为还差 12”，而不是只降低透明度。

普通可逆行动直接执行；突破等高风险行动在当前区域展开确认面板，重述消耗、概率与失败结果，确认与取消按钮并列。新局、覆盖或清除存档使用明确的二次确认，焦点进入确认区域，关闭后恢复原焦点。确认方式依最终规则裁定，不对每个日常点击弹窗。

## 完整状态反馈
| 状态 | 页面表现与操作 |
| --- | --- |
| 首次加载 | 展示明确加载提示，主操作不可重复提交；失败后保留重试入口 |
| 请求进行中 | 按钮显示“进行中…”，锁住会改变状态的操作，避免并发行动；保留可读状态与历史 |
| 成功 | 当前行动附近显示具体结果、资源增减和修行进展，适度高亮变化；存档成功后才显示已保存 |
| 条件不满足 | 按钮禁用且相邻显示原因，键盘与读屏可读取条件；状态更新后重新判断 |
| 规则拒绝 | 显示服务端可读原因，刷新权威状态，不伪造本地结果 |
| 网络或服务失败 | 明确“行动结果尚未确认”或契约规定的失败语义；不自动重试写操作，先重新获取状态再允许用户决定 |
| 空记录 | 提供“修行尚未开始”类简短说明，不伪造经历 |

状态改变通过温和的 `aria-live` 通知；错误信息使用可见文字并保留足够时间。所有按钮保留焦点样式、可用键盘操作，图形装饰不抢占读屏内容。

## 窄屏与动效
约 760px 以下变为单栏，顺序为当前目标、关键状态、行动、详细资源与记录；次要状态可折叠但主要消耗不可藏起。操作按钮最小触达高度 44px，长中文文本可换行，不依赖横向滚动、悬停或极小图标。确认与错误提示紧邻触发动作，避免被固定栏遮挡。

动效控制在轻微淡入、进度过渡和结果高亮；尊重 `prefers-reduced-motion`。不以自动轮播、闪烁或长动画延迟操作。

## CSS 自给资源与实施边界
用 CSS 渐变、细线、伪元素与简单山形剪影表达雾、远山与纸张边缘；装饰透明度低，不覆盖正文。必要图标可用短文字或本地内联 SVG，保持单色一致，无外链。首版不引入音频和大型背景图片，避免授权与加载成本；后续用户确定美术方向后再替换。

后续前端独占 `static/` 范围，文件名与入口服从技术契约。业务规则、随机判定、存档与状态版本由后端决定；前端只提交动作、渲染权威结果。正式实施前需要：状态字段与动作列表、条件/成本/风险格式、错误响应、存档及新局语义、重复请求处理规则。

## 验收建议与风险
验收覆盖桌面和窄屏实际浏览器：完整主路径可操作、无横向溢出、成本条件清晰、所有请求状态可观察、重复提交被阻止、键盘焦点可见、错误可恢复。高风险确认、新局确认、刷新后恢复与记录显示需与 QA 独立验证。

主要风险是状态字段或规则反复变化导致 UI 返工，以及将所有数值常驻造成密度过高。通过先冻结最小接口、仅突出当前目标与关键状态、细节按需展开控制。当前仅方案评审，尚未进行页面运行或无障碍验证。

## 交叉评审与 PM 裁决
- 策划提案的三种起始禀赋增加首次理解负担，与视觉方案的快速进入主路径存在分歧。PM 已裁决仅姓名输入，默认“归墟客”，不提供出身或禀赋选择。
- 策划提案采用确定性突破，原视觉方案为概率/高风险动作预留的突破确认会增加无用步骤。PM 已裁决突破直接执行，页面明示条件和结果；只有新局和手动载入使用确认。
- 架构提案允许网络超时以同 request_id 重试，与前端“先刷新再决定”的早期建议需要统一：刷新无法单独判定原请求是否完成。建议同一载荷保留 request_id 并允许明确的重试原请求，禁止生成新 ID 自动重放；409 则重新获取状态并由玩家重新选择，最终以 API 契约为准。
- 架构的自动备份/命令恢复与用户手动存档是不同概念，界面不能混称。PM 确定 SQLite 自动保存及一个手动 slot；界面区分“当前进度已保存”与“手动存档时间”，手动载入前说明将覆盖当前进度，不宣称具备未经验证的自动灾难恢复。
