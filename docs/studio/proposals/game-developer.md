# 开发工程提案（待项目经理确认）

## 范围与前置条件
目标为 HTML/CSS/JavaScript + Python 单人本地中文文字修仙游戏。此文只提出实施建议，不替代 GDD 或接口契约；未开始代码。后端由本岗位独占，前端由视觉岗位独占，公共契约由项目经理协调。

## 精简实现路线
1. GDD 明确初始状态、行动条件、消耗收益、失败规则及最小可玩闭环；架构师给出状态结构、动作标识和 HTTP 响应格式。
2. 先实现可独立调用的纯规则层，再接入持久化与 HTTP。Python 同源提供静态页面和 JSON API，默认仅监听本机，无外部 API、CDN、账号、数据库服务或付费依赖。
3. 提供读取当前状态、提交行动及受控新局入口；一次行动返回完整权威状态和本次日志，前端只呈现后端结果，不自行计算资源。
4. 使用临时存档进行端到端验证，联调真实浏览器操作；QA 独立验证后再处理缺陷与交付。具体模块和依赖以最终架构为准。

## 规则与存档风险
- 概率、回合推进和资源扣除统一在后端处理，校验成功后一次提交；失败请求不得留下部分变更。边界值、不足资源、达到上限和结局后行为须由 GDD 明确。
- 建议保存版本号、递增状态版本和必要随机结果，UTF-8 JSON 原子替换；保存失败不得向用户报告行动成功。不要依靠浏览器关闭事件保存。
- 存档载入应验证结构与数值范围；损坏时显示可诊断错误并保留原件，不静默清空。开发与测试存档隔离，不覆盖玩家进度。
- 同一存档的修改须串行化；若允许多标签页，应以状态版本拒绝过时提交，避免后写覆盖前写。

## 防重复扣费与联调约定
- 前端行动进行中禁用提交，始终使用服务端状态刷新资源；这只能改善体验，不能作为正确性保证。
- 建议每次用户意图携带唯一 request_id 和 expected_revision。后端在同一锁或事务内校验、执行、保存状态及去重结果；相同 ID 的重试返回原结果，不重复扣除行动资源。
- 同一 ID 携带不同动作或参数应拒绝；过期版本返回明确冲突及最新状态。超时后复用原 ID 重试，不生成新 ID。去重记录需与状态一起持久化且有明确保留规则。
- 契约须固定中文展示文本与机器动作标识的分工、错误码、空存档行为、重置确认、数字边界和日志顺序；不要让前端依赖错误文本判断逻辑。

## 可测试性与验收建议
将随机源与存档路径作为可注入依赖，测试固定随机结果而不依靠概率碰运气。规则测试覆盖正常收益、前置条件失败、资源边界及闭环终点；存档测试覆盖重启恢复、损坏输入和写入失败；API 测试覆盖非法输入、重复请求及状态冲突。实际启动后验证首页、状态读取和至少一条完整行动链。测试结果与未验证项分别报告，不以接口返回 200 代替玩法验收。

## 交叉评审与实施准备
已阅读策划、架构、视觉与 QA 提案。遵循 PM 新裁决：标准库 HTTP + SQLite，config/rules/storage/server 分离；确定性规则、无出身选择；每次行动自动保存，并提供手动 save/load slot；request_id 与 revision 持久化。本文件前述 JSON 文件存档仅为早期建议，已由 SQLite 事务方案替代。暂不编写代码，等待 GDD 与 API 冻结。

1. **冻结读档与幂等语义。** 架构契约应明确手动 slot 与当前进度分离：save 复制当前快照，load 在同一 SQLite 事务中恢复快照、分配新 game_id、继续递增 revision，并保存请求去重结果。旧页面写请求必须拒绝；同一次 load 重试不可重复生成实例。验收应覆盖“存档 → 行动 → 读档 → 重发读档 → 旧页行动”，确认恢复完整且不重复执行。无需在首版实现复杂自动数据库替换恢复。
2. **向前端直接提供可展示的行动定义。** 策划冻结每项成本、收益、条件和战斗顺序；API 返回动作 ID、中文名、可执行状态、禁用原因与说明，前端无需复制规则判断。视觉方案中概率提示与出身内容须随确定性裁决删除；网络结果不明时保留同一 request_id 的明确重试入口，不能刷新后静默当作失败再次扣除资源。
3. **为 QA 留出独立公开路径。** 以新档开始的合法行动序列验证完整闭环，HTTP 服务接收独立数据库路径并使用临时端口。GDD 应同时写出终局允许动作及败退后的免费恢复路线；QA 从公开接口/页面验收，不需修改存档。后端文件与 tests/、static/ 保持各自岗位独占，联调只通过冻结契约及 PM 转交缺陷。
