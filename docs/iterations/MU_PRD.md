# MU_PRD：多用户在线化（增量 PRD）

版本：草案 v1 · 作者：产品经理 · 日期：2026-10-21
范围：只描述相对现状（v1.2 + R5 + V4）的变更。技术栈不变：Python 标准库 HTTP + SQLite + 原生 JS，不引入第三方包或付费账号。

## 1. 背景与现状（已核实）
- `server.py`：全局单一 `Store`；`GET /api/state`、`POST /api/new-game|action|save|load` 均无身份。Host 白名单仅限本机/监听地址，另有 `Origin` 和 `X-Game-Client` 校验。
- `game/storage.py`：`data/game.db` 的 `current` 表固定单行 `id=1`（`state` 加 `slot` 手动检查点）。`requests` 表以 `request_id` 为全局主键。`write()` 已是 `BEGIN IMMEDIATE` 原子事务，带 revision 和 request_id 幂等，所以每个动作已即时落库。
- 因此需求四主要是把现有行为在语义和 UI 上表达出来并加以验证。需求一、二是主体工作。
- 单机字眼约 301 处，分布在 78 个文件中：`static/app.js`、`static/index.html`（工具栏和确认弹窗）、`server.py`、`game/*.py` 的报错和事件文案、`scripts/launch.py`、tests、README 和 docs。具体清单由架构师产出，本 PRD 只定范围和验收。
- longline 模式下 `load` 只恢复安全位置，保留成长、资产、经济和奖励资格（`growth.load_checkpoint`）。free 模式完整回滚。

## 2. 目标与非目标
### 目标
- G1 账号与会话：每个玩家用账号登录，服务端鉴权，所有游戏接口必须携带有效会话。
- G2 严格隔离：每个账号拥有独立的进度、revision 和请求账本，任何路径都不能读写他人数据。
- G3 服务化语义与自动保存：界面不出现单机字眼。每次交互结束后由服务端立即持久化，并向玩家显示可见反馈。

### 非目标（本版不做）
- 玩家间 PVP、交易、拍卖互市、跨账号排行、聊天和好友。NPC 模拟不得伪装真人（AGENTS.md）。
- 邮箱或手机验证、第三方登录（OAuth）、找回密码邮件、验证码服务，因为都需要外部账号或费用。
- 多设备同时在线的实时推送。多页面并发沿用 `STALE_STATE` 提示即可。
- 仙界、新玩法、数值改动。
- 分布式部署或换数据库，仍为单进程加 SQLite。

## 3. 用户故事
1. 作为新玩家，我想用用户名和密码注册并进入游戏，以便在自己的账号下开始修行。
2. 作为老玩家，我想在任何浏览器登录后看到自己的修行进度，以便换设备继续。
3. 作为玩家，我想每次操作后进度自动保存，并看到“进度已同步”，以便断网或关页后不丢进度。
4. 作为玩家，我想会话过期或被登出后得到明确提示并重新登录，而不是看到莫名报错或空白。
5. 作为运维或原单机玩家，我想把原有 `data/game.db` 的进度安全归入指定账号，且不丢失、不被他人看到。

## 4. 功能需求

### 4.1 账号与会话（P0）
| 编号 | 需求 |
|---|---|
| A1 | 系统 must 提供注册：用户名 3–20 位（中文、字母、数字、下划线），不区分大小写唯一；密码 8–64 位。重名返回明确错误，且不泄露他人信息。 |
| A2 | 系统 must 提供登录。密码只存加盐的慢哈希（标准库 `hashlib.scrypt` 或 PBKDF2-HMAC-SHA256，参数写入记录以便升级），比较用 `hmac.compare_digest`。禁止明文或可逆存储。 |
| A3 | 登录成功后 must 签发随机会话令牌（`secrets`，至少 128 位），经 HttpOnly、SameSite=Lax 的 Cookie 下发（在 HTTPS 下加 Secure）。服务端只存令牌哈希，不存明文。令牌不得出现在 URL、日志和 JS 可读存储中。 |
| A4 | 会话 must 有过期：空闲 7 天滑动续期，绝对上限 30 天，具体值可配置。过期会话访问接口返回 401 `SESSION_EXPIRED`。 |
| A5 | 系统 must 提供登出，服务端立即作废当前会话。登出后复用该令牌返回 401。 |
| A6 | 系统 should 提供改密（需旧密码）。改密后作废该账号其他所有会话，保留当前会话。 |
| A7 | 登录和注册 must 有失败限流：同一用户名加来源连续失败 5 次后，锁定 5 分钟，返回 429。错误文案不区分“用户不存在”和“密码错误”。 |
| A8 | 所有 `/api/*` 游戏接口（state、new-game、action 及后续接口）must 先鉴权，再校验 Host、Origin 和 X-Game-Client。只有 `/api/health`、静态资源和注册、登录接口免鉴权，且不返回任何用户数据。 |
| A9 | 系统 could 提供“注销账号并删除进度”。该操作需二次确认，默认不做，列入待决问题。 |

### 4.2 鉴权失败与断线重连体验（P0）
- B1 收到 401 时，前端 must 保留当前页面状态，弹出登录面板，文案如“登录已过期，请重新登录”，不得显示原始错误码或空白页。重新登录后回到登录前的界面。
- B2 离线或请求超时时，顶部状态 must 显示“网络中断，正在重连…”。动作按钮暂时不可点，避免重复提交。
- B3 重连后 must 自动 `GET /api/state` 拉取最新进度。用户在断线前最后一次提交的请求，用同一个 `request_id` 重试，由服务端幂等去重，不会重复生效。
- B4 `STALE_STATE`（另一页面已更新）的提示文案去掉任何单机含义，改为“进度已在其他页面更新，已为你刷新到最新”，并自动刷新。
- B5 登录或注册表单 must 区分字段错误和服务错误。提交中禁用按钮，防重复提交。

### 4.3 数据隔离（P0）
- D1 每个账号 must 拥有独立的游戏状态行、`revision` 计数和请求账本。`requests` 的唯一键 must 改为 `(user_id, request_id)`。同一 `request_id` 在不同用户间互不影响，也不会泄露彼此是否存在。
- D2 存储访问接口 must 以 `user_id` 为必选参数，且 `user_id` 只能来自服务端会话，不得来自请求体、URL 或头。请求体带 `user_id` 等未知字段，沿用现有“未知字段拒绝”。
- D3 SQLite 写事务仍用 `BEGIN IMMEDIATE`，按账号锁定的写入不得因并发导致串写。两个账号并发操作，各自 revision 独立递增。
- D4 `world` 单机世界、序章状态、`actions_taken`、日志、成就和称号等全部按账号私有。本版没有任何全局共享的可变游戏状态。时间驱动的结算（吐纳修为、cadence）按账号各自计算。
- D5 任何响应、日志和错误信息 must 不含其他账号的名称、状态或 ID。服务端日志不得记录密码和令牌。
- D6 数据库升级 must 遵循 AGENTS.md：先停服备份，再显式迁移；未知 schema 拒绝启动并保留原件，不得静默清档。

### 4.4 “手动检查点”去留与新语义（P0 决策，推荐如下）
推荐：**删除玩家可见的手动存档和载入功能**，包括 `/api/save`、`/api/load` 端点、工具栏的“手动存档”“载入手札”“保存位置”“返回检查点”以及确认弹窗。理由：
1. 服务端已在每个动作后原子落库，手动保存没有额外价值，反而暗示“不点保存会丢”，与“自动保存”相矛盾。
2. “载入”是回滚语义，属于单机玩法。在线账号下，回滚会和 revision 单调、请求账本不可回退这条约束冲突。longline 模式下它本来就只恢复安全位置，语义不清。
3. 回滚可被用来重掷随机结果（刷战斗、刷奇遇），在服务化后破坏公平和数据一致。
4. 删除可减少一个接口、一份 `slot` 数据和多处确认交互，攻击面和测试量都更小。

保留项与过渡：
- `slot` 列在库中保留但弃用，不物理删除，不做破坏性迁移，以便回滚和审计。
- 若策划认为“脱困”确有必要，另行以游戏内机制提供，如“回到安全地点”，作为普通 action，走正常 request_id 和 revision，并按游戏内道具或冷却处理。该机制 could，不属于本 PRD，需主策划另立需求。
- 备选方案（不推荐）：保留机制但改名为“记录安全位置 / 回到安全位置”。前提是明确它不是回滚。成本是保留 `slot`、两个接口和 UI，而且仍有“手动”暗示。

### 4.5 自动保存与可见反馈（P0）
- S1 每个会改变状态的请求（new-game、action）must 在服务端同一事务内完成持久化后才返回成功。响应表示“已保存”的前提是事务已提交，`synchronous=FULL` 保持不变。
- S2 前端 must 不再调用任何“保存”接口。进度状态只由响应驱动，不由用户手动触发。
- S3 顶部 `save-status` 区域改为同步状态指示，状态机如下：
  - 提交中：“进度同步中…”
  - 成功：“进度已同步”（展示最近一次成功时间，约 3 秒后淡化为常驻小标记）
  - 失败或断线：“同步失败，正在重试…”，重连成功后恢复为“进度已同步”
  - 服务端持久化失败（`SAVE_FAILED` 类）：“进度保存失败，请稍后重试，当前操作未生效”，且不得显示为成功。
- S4 异常保证：服务进程在请求处理中被杀，重启后账号进度只能是该动作前或该动作后的一致状态，不得出现半写。
- S5 页面关闭或刷新后重新登录，进度 must 等于最后一次已提示“已同步”的状态。
- S6 离线期间的动作不在客户端排队本地保存，必须等重连后由用户重新操作，或仅重试最后一个未确认请求。本版不做离线队列。

### 4.6 文案与术语统一（P0）
禁用词与替代词（适用于所有玩家可见处：界面、提示、报错、事件日志、启动脚本输出）：

| 禁用词 | 替代词 / 做法 |
|---|---|
| 存档、本地存档、手动存档 | 进度 |
| 保存成功 / 存档成功 | 进度已保存 / 进度已同步 |
| 读档、载入存档、载入手札 | 删除该功能。必须出现的场景用“登录后恢复进度”“继续修行” |
| 返回检查点、检查点、保存位置 | 删除该功能。游戏内回城机制用“回到安全地点” |
| 存档损坏、存档无法读取 | 进度暂时无法读取，请稍后重试或联系管理员 |
| 存档版本不受支持 | 进度数据版本不受支持，已保留原数据 |
| 单人、本地、单机 | 删除，或改为“修行者”“你的账号” |
| 请保留存档并检查日志（管理员向） | 请保留数据并检查服务日志（运维可见处允许“数据”二字，不用“存档”） |
| “展卷”“读取你的修行手札”等加载文案 | 保留风格，改为“正在同步你的修行进度” |

规则：
- T1 管理员和运维文档中也 should 遵循同一术语，但历史迭代文档（`docs/history`、已归档的 R3/R4 报告）不改写。
- T2 CLI 参数 `--migrate-save` 的帮助文案 must 去掉“存档”。参数名为兼容保留，可增加别名 `--migrate-data`，旧名在一个版本内继续可用。
- T3 内部标识符（如 `slot`、`save` 字段）不要求改名，只要不进入玩家可见层。需要时由架构师清点后统一处理。
- T4 `/api/state` 响应里的 `save`、`profile.load_policy` 字段 must 不再对前端暴露单机语义。删除字段或改为 `sync`。

## 5. 存量单机数据处置（P0）
现状：`data/game.db` 为单个无主进度（`current` id=1，加 `requests` 账本）。
策略（推荐）：
1. 升级到多用户 schema 前，系统 must 先停服备份：复制出带时间戳的 `game.schema2.*` 备份并校验一致，再做显式迁移（`--migrate-*`）。沿用现有 `_backup_locked` 机制。
2. 迁移后旧进度放入“待认领”区（`legacy_unclaimed`），**不绑定任何账号**，任何账号登录都看不到它。
3. 认领只能由持有服务器文件权限的运维通过命令行完成，例如 `--claim-legacy <用户名>`。认领前账号必须已存在，且该账号尚无进度或使用 `--force` 才覆盖，覆盖前先备份。
4. 不采用“第一个注册的人自动得到旧进度”，因为在公网部署下会被抢占，属于串用风险。
5. 旧 `requests` 账本随进度一起归属被认领的账号，未认领前不参与任何幂等判断。
6. 未认领期间旧数据保留，不删除、不清理。认领后原待认领记录标记为已认领，保留一份只读备份。
7. 迁移失败 must 终止启动并保留原件。损坏或未知 schema 同样拒绝，禁止静默清档。

## 6. 范围外但需联动的非功能项
- N1 部署：默认仍监听 127.0.0.1。若要公网或局域网提供服务，Host 白名单 must 可配置（如 `--allowed-host`），并建议经反向代理提供 HTTPS，因为会话 Cookie 与密码在明文 HTTP 下可被窃听。本 PRD 不要求自带 TLS。
- N2 CSRF：写接口继续要求 `X-Game-Client` 加 Origin 校验，Cookie 使用 SameSite=Lax。
- N3 性能：单进程 SQLite，目标 50 个并发活跃账号时，动作接口 p95 小于 300ms（不含网络），登录哈希参数调到单次约 100–300ms。
- N4 所有新增按钮和表单有后端实现；新增后端能力（注册、登录、登出、改密）有 UI 入口（AGENTS.md）。一屏不滚动的 V4 界面约束保持，登录页和账号菜单需适配 10 个已测视口。

## 7. 可验收标准（均可测）
账号与会话
- AC1 未携带会话访问 `GET /api/state`、`POST /api/action|new-game`，全部返回 401，响应体不含任何进度数据。
- AC2 注册后可登录。重名（含大小写差异）注册返回明确错误，不创建第二个账号。
- AC3 数据库中搜索不到明文密码和明文令牌。随机抽查账号，密码字段是带盐哈希且各账号盐不同。
- AC4 登出后，用旧令牌访问返回 401。把会话 `expires_at` 调到过去后访问返回 401 `SESSION_EXPIRED`，前端出现登录面板，页面状态不丢失。
- AC5 连续 5 次错误密码后第 6 次返回 429，即使密码正确；锁定到期后恢复。“用户不存在”和“密码错误”返回相同文案和状态码。
- AC6 改密后旧密码不可登录，新密码可登录，该账号其他会话失效。

数据隔离
- AC7 账号 A、B 各自新建游戏并执行不同动作序列，A 的 state、revision、日志、`actions_taken` 与 B 完全独立，互不出现对方的名称或事件。
- AC8 A 和 B 使用同一个 `request_id` 提交不同动作，两者都成功且各自生效一次，不出现 `REQUEST_ID_REUSED`。
- AC9 A 的会话令牌带上 B 的信息（请求体加 `user_id` 或类似字段）会被拒绝；任何接口都不存在可选择他人 ID 的参数。
- AC10 A、B 并发各发 100 个动作（线程或多进程），完成后两人 revision 各为各自动作数加初始值，无丢失、无串写、无数据库锁错误。
- AC11 吐纳修为等时间驱动结算，A 离线不影响 B，且 A 的结算只在 A 的数据上发生。

自动保存
- AC12 每个 action 响应成功返回后，立刻另开连接直接读库，库内 revision 和 state 与响应一致。
- AC13 故障注入（在测试用临时库中，在提交前后分别中断）：提交前中断后，重启读到的是动作前状态；提交后中断，读到的是动作后状态；没有半写。不对玩家真实数据注入故障。
- AC14 断线重放：客户端发送请求但丢失响应，用同一 `request_id` 重试，返回 `duplicate=true`，状态只生效一次。
- AC15 前端源码和网络日志中不再调用 `/api/save`、`/api/load`；该两个路径返回 404（或 410）。
- AC16 浏览器验证：完成一个动作后顶部出现“进度同步中…”再变为“进度已同步”；模拟服务端存储失败时显示“进度保存失败…”，且不显示已同步。

文案一致性
- AC17 玩家可见层静态扫描（`static/**`、`server.py` 与 `game/**` 中会进入响应的字符串）不含“存档、读档、载入存档、载入手札、本地存档、检查点、保存位置、单机”。白名单仅限历史归档文档和代码注释，需逐项列出。
- AC18 运行时抽检：遍历所有错误码触发路径，响应 `message` 不含禁用词。浏览器端抓取各页面和弹窗的可见文本，也不含禁用词。
- AC19 `python -m tests.parallel` 全量通过，新增 AC1–AC18 对应测试且无跳过。浏览器套件（Playwright）若本机可运行则必须通过，不可运行须在测试报告中如实写“未运行”。

存量数据
- AC20 用一个含有进度的 schema2 `game.db` 副本升级：备份文件存在且逐字节校验通过；升级后任何新注册账号都读不到该进度；运维执行认领命令后，指定账号读到的 state 与升级前逐字段一致。
- AC21 迁移中途失败的模拟下，原库保持不变，服务拒绝启动并给出不含禁用词的提示。

## 8. 验证方案思路
- 多账号隔离：白盒测试直接调用 `dispatch`，沿用 `tests/support.py` 的临时数据目录和 `TestClock`。建 2 到 3 个账号，交叉请求（用 A 的令牌、B 的 request_id、篡改请求体），断言 AC7–AC10；并发用线程池。另做一条“库内对账”：直接查询表，确认每条记录的 `user_id` 与操作者一致。
- 保存时机：每个 action 后直读库对比；用临时库注入提交前后异常；断线重放测试幂等；浏览器测试观察状态指示的三态。
- 文案一致性：建一个测试用例，对白名单外所有源文件做禁用词正则扫描；再以全部错误码触发和浏览器可见文本抓取做运行时抽检；清单由架构师的改造清单生成，保证测试和清单同步。
- 迁移：用夹具生成 schema2 库，演练备份、迁移、认领和失败回滚。
- 回归：既有 R3/R4/R5/世界测试在账号化后按账号上下文改造，不删除断言。

## 9. 风险
| 风险 | 影响 | 缓解 |
|---|---|---|
| 约 300 处文案分布广，漏改或误改（如日志、docs 引用） | 验收失败或文档失真 | 以扫描测试兜底；历史文档用白名单排除 |
| `Store` 由单例改为按账号读写，几乎所有测试和 `tests/support.py` 受影响 | 工作量和回归面大 | 架构师先给出接口方案，QA 并行改造测试夹具 |
| 明文 HTTP 下暴露密码和会话 | 账号被盗 | 默认仅本机监听；对外部署文档要求 HTTPS 反代 |
| 旧进度认领被滥用或误认领 | 串用 | 仅运维命令行、认领前备份、不自动绑定 |
| 无邮箱，忘记密码无法找回 | 玩家丢失账号 | 提供运维重置命令；是否做恢复码见待决问题 |
| 删除手动检查点会减少“后悔药”体验 | 个别玩家不满 | 以游戏内“回到安全地点”机制替代，由策划评估 |
| 单进程 SQLite 在较多账号下写锁争用 | 延迟上升 | `BEGIN IMMEDIATE` 加 busy_timeout，已有；必要时拆分每账号一库（本版不做） |

## 10. 待决问题（需主理人 / 用户确认）
1. 检查点去留：是否同意推荐的“删除手动存档与载入功能，并弃用 `slot`”？是否需要游戏内“回到安全地点”机制（若需要，由主策划另立需求）？
2. 部署场景：仅本机或局域网多人，还是公网？这决定 Host 白名单可配置、HTTPS 与限流强度的优先级。
3. 存量 `data/game.db`：是否同意“迁移后进入待认领区，由运维命令行认领”，而不是首个注册账号自动继承？
4. 是否需要注册开关或邀请码，防止陌生人自助注册？
5. 找回密码：仅提供运维重置命令，还是加“注册时生成一次性恢复码”（无外部依赖）？
6. 是否需要“注销账号并删除进度”（A9）？
7. 会话时长（空闲 7 天、上限 30 天）和登录限流参数是否可接受？
8. 同一账号是否允许多设备同时登录？推荐允许，写入冲突沿用 `STALE_STATE`。
9. 用户名是否允许中文？推荐允许，但需做 Unicode 规范化（NFKC）避免相似字符冒名。
10. 玩家角色名（new-game 的 `name`）与登录用户名是否分离？推荐分离，角色名可重名。
