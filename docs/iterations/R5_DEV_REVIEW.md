# R5 自动战斗与推进图：开发交叉评审

状态：仅方案评审；未修改应用代码、存档、数值、测试或发行包。依据当前world/rules/loot/journey、R4_API与岗位约束。规则和兼容范围须PM冻结后实施。

## 结论与最小落地路径

应做服务端确定性战斗模拟与结构化战报，再让前端播放基础人物/敌人、技能与血蓝条。不能用定时点击旧攻击按钮冒充自动战斗，也不能让GET、动画速度或浏览器可见性决定资源、冷却和结算。

建议抽取一个完整逻辑回合的纯resolver，保留当前伤害、敌意图、毒盾汲灵、胜负结算顺序作为共享基础；自动调度器从战斗快照中的技能/策略决定该回合行动，再调用resolver。旧手动战斗也可调用该resolver，不复制两套毒伤/结算代码。冷却和自动调度放新combat模块，world负责世界时钟/AI/任务观察，loot/cadence仍独占掉落、Boss和资格账本。

先冻结调度/回合语义→纯模拟与世界接入→结构化投影和基础回放→独立路线/旧回归。第一版建议一个战斗主技能槽、明确的防御/回灵策略，以及已有两法宝槽的主动效果，不先加入任意技能编程、多角色自由站位或物理碰撞。

## 技能CD与法宝优化建议

- 一个逻辑回合包含玩家决策、至多一次主行动、必要伴随法宝效果、敌方机会、状态/冷却结算；角色和NPC双方都按同一时基自动选技。前端帧率不参与规则。
- 每个技能标明优先级、MP成本、CD、目标条件。MP不足或技能不可用必须有确定性基础攻击/回灵fallback，不应HTTP报错卡死整块。防御、清毒、破盾属于可理解的策略条件，并在开战预览显示，避免自动模式只会无限强攻。
- “常驻短CD/爆发长CD”建议解释为已装备法宝的周期技与爆发技，而非再加两套装备槽。沿用本命/护持槽与修炼/战力二选一路径；修炼宝仍只给持续速率，不能无代价同时获得战斗技能。短CD不必每回合闪烁，常驻应是自动循环，不是永远无冷却。
- 冷却以战斗tick计，入场明确初始可用/初始延迟；何时递减必须写死，CD=3应给第1/4/7回合可用例子。暂停、重连、改倍速不恢复CD；战斗结束才销毁该场冷却。若爆发开场可用，Boss奖励和低难速杀须重新测，不能认为旧平衡自动成立。
- 丹符默认为不自动消费，开战选择可见预算/触发阈值（如本场最多丹2、破盾符1），服务器冻结预算；实际使用仍扣真实库存，不能把“自动”变成无限药。策略只能使用确实有的物品；零库存回退合法行动。镜像演武仍扣镜像库存。
- 通过准备策略和构筑影响结果，比战中不停弹确认更契合全自动。建议图形上展示下一技能/CD/反制触发原因与战斗日志，而非只放攻击动画。

## 机制、资源与自动化易错点

1. 现毒规则是旧毒先跳、存活再刷新2；第一次新毒不当回合跳。防御仅免新毒，丹清旧且当次免重挂，魂跳敌仍跳旧毒；玩家先击杀则整次敌机会/毒不发生。自动技能调度不应在同回合偷偷补一次药又输出，除非策划明确牺牲/独立行动成本。
2. 炉盾物理溢本体，火符有盾2A无溢出、无盾1.5A；伴随法宝先后会改变是否破盾，需冻结固定序列并可回放。汲灵只在真实常击且未防/未魂时扣min(6,MP)，不能因为自动选技失败反复扣蓝。
3. 现世界Boss个人伤害只记攻击主行动，同行不计。法宝新增攻击必须使用明确source=player_equipment/NPC，不从总敌HP差猜玩家伤害；每个hit做min(剩余HP)且12回合终结只一次。退出/死亡也走同finish_boss，不清零重开成绩。
4. 战败仍HP1/回安全地、清探索并释放副本预约；撤退无反击、释放预约，Boss先结算本次真实成绩。中断重连保留已提交回合，不回滚药品、CD、伤害或资格。
5. 自动完整手战应生成真正手战证明；已解锁扫荡继续使用原同章难证明与单次共享奖励。扫荡不运行回合、不消耗丹符、不虚构技能CD/手战回合，也不计s6特殊手战目标。不能把auto一场当扫荡而免掉真实风险。

## 建议数据与API

与架构初评一致：服务端bounded advance，每POST推进固定/上限3—5个完整逻辑回合，前端自动续请求但不选择每一旧动作；回放/倍速/跳过只是显示。这样既有可见过程和中途撤退，也不会单请求无限阻塞。

战斗快照建议含mode/version/battle_id/cursor/构筑快照/策略/技能CD/状态/最近一块事件；世界引用和现有Boss/run身份保留。新动作候选`world_battle_advance{battle_id,expected_cursor}`，仍使用request_id+expected_revision；cursor不匹配拒绝，不重复仿真。返回事件给稳定id=battle_id:cursor:index、source/target、skill、数值和before/after；客户端只播放已提交事件。

终战battle清空后，最近有限份battle_report保存最后事件与结局摘要，重连仍能看到最后击杀/奖励；报告不能成为再领奖或回放结算指令，不无限存全历史。图形投影建议actor{name,hp,max_hp,mp,max_mp}、skills{label,cd_remaining,ready_reason}、statuses、intent/target、timeline、outcome与真实dungeon nodes；不把裸state发给UI自算伤害。

关键重构：当前world.apply_action一次HTTP只tick/AI+1，若一块推进5回合不能只增长一次，也不能每动画帧增长。应按实际逻辑回合逐次tick/AI，再按真实状态差分观察物品使用/终战；外层不能再额外+1。持续成长仍按单个服务端now结算，仿真回合不能伪造离线时间或发行动XP。关系冷却、NPC经济、活动/故事计数、logs/actions_taken须统一计数定义，提前由PM冻结。

## 必要验收与待裁决

验证相同初态/策略、分块1/3/5、断线重连、重放请求得到同战果/药耗/CD/奖励；GET、倍速、回放不修改任何资产。覆盖全部战斗kind，毒旧新刷新/火符破盾/汲灵0MP、药预算耗尽、镜像还原、12回合Boss伤害归属与best差额、败退释放、活动/故事只计一次、扫荡不受新动画影响。沿R4原181回归评估影响，不能删旧有效断言；新增自动玩法可达性必须真实合法准备路线实证，不以旧手动胜利代替。

待PM冻结：旧序章/free的自动适配范围、主行动与法宝触发先后、CD例子/战力宝新增伤害预算、丹符默认与预算UI、每逻辑回合world时钟/计数口径、分块上限及战报保留上限。开发目前未开始应用实现。

## 与策划、架构的首轮交叉结论

策划初案采用ready_at=t+CD、初始ready0；每玩家机会1主行动，法宝与NPC独立通道，丹符默认0预算，场内构筑/策略锁定。拟覆盖序章与全部world kind，free旧纯规则保留，可显式委托；已有手战可用旧策略委托完成，不重置状态。以上目前是候选，不是数值已冻结。

架构采纳bounded推进与有界last_battle_report，建议默认1—3机会、快进最多8待实测；旧battle首个授权POST分配稳定ID，GET不生成或写入ID。开发补充接受：每场必须有最大合法机会与明确僵持终态，避免低伤/循环防御自动无限推进NPC经济；自动继续副本或新run须单独明确授权，绝不默认无限开局。旧ongoing使用原resolver/状态，下一场才进入新auto形状，迁移不重置Boss12机会或镜像物资。
