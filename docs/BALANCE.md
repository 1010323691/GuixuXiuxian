## HTTP 实跑方法与证据计划
1. 待 PM 告知服务入口/启动方式，用独立临时数据库，不接触玩家或 QA 数据。每条路线新建干净实例或新局，记录初始 revision；优先分别使用干净实例，便于核对 revision 预期。
2. `GET /api/health` 与 `GET /api/state` 确认可用；所有写请求携带 `X-Game-Client: guixu-web`、JSON、新唯一 request_id 和上次响应的 expected_revision。
3. 仅调用 `/api/new-game` 与 `/api/action`，travel传region、challenge传enemy，其余params={}。每次验证HTTP成功、响应ok、权威状态增量和actions_taken；记录每个检查点，不因200就认定玩法通过。
4. 若被拒绝或出现与预期不符，停止该路线并记录动作、前后状态及错误，不直接修存档或改变路线掩盖。向 PM 说明属于设计算术偏差、契约差异还是疑似实现缺陷。
5. 原始请求序列与检查点输出存放临时证据目录；本文记录实际启动命令、运行日期、关键实跑状态、通过/失败/未执行项及证据路径。公开HTTP实跑不能代替真实浏览器或独立QA测试。

## 体验评审标准
- 新玩家能从当前目标读出下一步骤，突破条件不会只显示“不可用”；第一轮修炼与后段修炼不要求无意义等待。
- 敌方意图明确，强攻、防御、丹药各有可解释用途；强攻不可因资源不足悄悄变普攻。终局前有合理容错，无强制刷药/升级。
- 挫败后能撤退或静养恢复，免费循环有效；数值上限与丹药溢出清楚，避免误认为所有药效都到账。
- 通关不清空角色，结局后可继续；探索重复文案与24次修炼可能产生重复感，记录为试玩观察项，不能用自动化响应速度推断真人体验。
- 10–20分钟仅设计目标；真人阅读、理解和操作时间未测。未进行用户试玩时不得宣称达到目标时长。
